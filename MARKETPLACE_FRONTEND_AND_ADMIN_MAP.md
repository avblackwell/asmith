# Marketplace and administration frontend map

Source review: 2026-09-28. This maps the supplied `operator_display` Java source to the Appsmith frontend in this checkout. It is a frontend implementation guide, not evidence that the Java service was built or contacted. The Java backend remains unchanged. The current integration routes use controlled responses in browser checks; deployment behavior still needs verification.

For the complete admin route, permission, screen, and backend-gap audit, see [Administration screens and backend contract](ADMIN_SCREENS_BACKEND_MAP.md).

## Decision

Use Appsmith's design system and selected page layouts for the catalog and administration screens. Keep the new frontend's marketplace transport and dashboard service. Build screen containers around the Java contracts rather than mounting Appsmith's Applications, Workspace Settings, Templates, or Admin Settings containers.

There are three different meanings behind the similar names:

| Name in this codebase | What it actually owns | Appropriate use here |
|---|---|---|
| Appsmith **workspace** | Applications, members, permission groups, logo, environment and workspace settings behind Appsmith `/v1/workspaces` APIs. | A visual model for a group administration layout, not the target data model. |
| Java **user group** | `ADMIN`/`MEMBER` membership and access to group-associated resources. Items can be associated with groups in the database and queried with a `group_id` catalog filter. | Present groups as **marketplace filters/audiences**. Include the seeded Public group when it is returned for the current user. Put group administration behind a settings action for authorized users. This is not an Appsmith application workspace. |
| Integration **`/workspace`** | Dashboard catalog, account-scoped browser drafts, and editor entry. | Keep as the current dashboard entry while adding a separate marketplace/admin navigation. It does not administer Java groups. |

The integration bootstrap intercepts every `/workspace/*` path before Appsmith's router and blocks Appsmith `/v1` and `/api` calls. New pages must be added to that bootstrap or another explicit integration route; a link to Appsmith's original `/workspace/{id}/settings` cannot work in integration mode. See [integration route selection](app/client/src/index.tsx:37), [API guard](app/client/src/integration/standalone/networkGuard.ts:15), and [existing entry](app/client/src/integration/workspace-entry/index.tsx:61).

## Backend action inventory

Paths below are relative to the deployed Java context (normally `/operator_display`). The main app resolves a session user through [SessionService](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/services/SessionService.java:17). Paginated lists use `search`, `cursor`, `limit`, repeated `sort`/`sortValue` and `filter`/`filterValue`, returning `{data, meta}`; this is not Appsmith's `{responseMeta, data}` shape. See [pagination parameters](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/data/query/PaginatedQueryParams.java:17) and [MarketplaceClient normalization](app/client/src/integration/marketplace/MarketplaceClient.ts:90).

**Filter combination constraint:** [PaginationDao](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/dao/PaginationDao.java:503) joins every supplied filter predicate with `OR`, even when the fields differ. Search is joined to that filter clause with `AND`. A request with `type=dashboard` and `group_id=7` returns all dashboards **or** all items in group 7, not just dashboards in that group. Filtering one page in the browser cannot restore accurate page data and totals. Until Java supports `AND` across distinct fields, use a single item filter such as `group_id` (optionally with search and sort), or a single `type` filter for the existing dashboard-only catalog. Do not combine group, type and tag facets in one request. The existing [DashboardWorkspaceService](app/client/src/integration/workspace/DashboardWorkspaceService.ts:81) appends `type=dashboard` to caller filters, so callers must not pass it `group_id` or `tags` expecting an intersection.

## Information architecture

```text
Marketplace
  All assets           dashboards | components | themes; search, sort, one filter at a time
  Group filters        accessible groups, including Public when returned
  Item details         preview gallery, author, metadata, ratings, open/install/apply
  My local drafts      browser-local dashboards, clearly marked local
  Group settings        General and Members, visible to group/system admins
Administration         only system admins
  Users                list and detail; add form reports backend errors
  Tags                 list, create, edit, delete
Workbench              existing dashboard editor and viewer
```

The shared product header and side navigation use Appsmith ADS. The marketplace is a full page; the workbench Tools panel remains an in-context asset picker. Owner and system-admin management actions are visible when metadata/session supports them; group-admin item rights are provisional because the item DTO lacks group IDs. The server's 403 remains authoritative. Catalog presence does not promise item access because the listing filter is disabled.

Use a separate `MarketplaceAdminClient`/`MarketplaceAdminService` (or a clearly separated extension of `MarketplaceClient`) to map Java group/user/tag DTOs. Keep browser UI components dependent on typed services and callbacks, as `DashboardCatalog` and `MarketplaceAssetPanel` already do. Do not dispatch Appsmith workspace/admin sagas. Share a paging/search view model across item, group, user and member lists; preserve Java's field names in transport and normalize them at the UI boundary.

The implemented route namespace retains `/workspace` for dashboard links and adds `/marketplace`, `/marketplace?groupId=…`, `/marketplace/items/:id`, `/marketplace/items/:id/manage`, `/admin/*`, and `/operations/*`. Group selection is catalog state, not a separate application workspace. These prefixes are in the integration bootstrap and API guard. Java group settings are outside stock `/workspace/:workspaceId/settings`.

## Contract gaps that shape the UI

**Filter semantics block combined facets.** The Java paginator connects all filter predicates with `OR` ([source](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/dao/PaginationDao.java:503)). For the first frontend group view, request `group_id` alone; search and a supported sort can still be used. A type or tag selector cannot accurately narrow a selected group until the backend query builder changes. This also affects the dashboard service when a caller supplies a tag filter. A backend fix should use `AND` across distinct fields and `OR` among repeated values of one field, with tests for `group_id + type`, `totalItems`, and cursors.

1. **Groups already work as catalog filters, but setting publication is missing.** The schema has `marketplace_item_user_group_assignment`, the item paginator accepts `group_id`, and test data assigns items to the seeded Public and other groups. That supports the proposed filtered marketplace UI for existing assignments. The production schema seeds a Public group, while test data adds member assignments; the main source does not show automatic Public membership for every real user. The item create/update DTOs have no group or visibility field and item metadata has no group IDs. No registered action assigns/removes a group. The create SQL sets `published_at` to `NULL`, no publish/unpublish route was found, and the list query does not require a non-null `published_at`; even the grouped sample items have `published_at=NULL`. Thus the current API cannot implement the user action “set this item to Public/published so it appears in that group.” It needs an implemented Java contract or another verified service. See [group assignment seed](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/resources/sql/test-data.postgres.sql:176), [group filter](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/dao/MarketplaceItemPaginationDao.java:90), [create DTO](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/data/marketplace/MarketplaceItemCreateRequest.java:14), [item metadata](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/data/marketplace/MarketplaceItemMetadata.java:30), [create SQL](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/resources/com/trplabs/cyflex/operator_display/dao/create-marketplace-item.sql:1), and [list query](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/dao/MarketplaceItemPaginationDao.java:30). The [wiki design](C:/Users/alexb/Downloads/backend/markerplace_backend/wiki/backend.md:15) describes status and visibility endpoints, and the [README](C:/Users/alexb/Downloads/backend/markerplace_backend/README.md:83) describes `/personal-files` publishing, but those routes are absent from the registered Java API in this snapshot.
2. **Catalog list is wider than item access.** The current-user filter in [MarketplaceService](C:/Users/alexb/Downloads/backend/markerplace_backend/src/main/java/com/trplabs/cyflex/operator_display/services/MarketplaceService.java:108) is commented out. UI filtering is useful for navigation but cannot enforce privacy. The main item subresource still checks access. Review this server behavior before treating the catalog as a private workspace feed.
3. **No exact owner filter.** The item paginator accepts `publisher_name` but not `publisher_id`, so it cannot prove a complete account-owned item list from stable numeric identity. Avoid treating a name search as an authorization or ownership boundary.

7. **No server-enforced content revision or type schema.** Item replacement overwrites the content key; Java does not parse dashboard/component/theme packages.
